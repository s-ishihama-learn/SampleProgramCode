データベースの排他制御についての質問です。
処理A、処理B、処理Cの3つの処理があり、それぞれ独立に動きます。各処理は１つだけでなく複数動く場合があります。現在は、ロックテーブルを使用して、処理A実行中は処理A、処理B、処理Cは処理待ち、処理B実行中は処理A、処理B、処理Cは処理待ち、というように制御されています。このため、処理待ちが多発して処理性能に影響がでています。
処理AはキーXとキーYでロックの制御が必要で、処理Bと処理CはキーYのみ（キーXの情報は持っていない）でロックの制御が必要です。
キー単位でロックする方法を提案してください。

---  

現在のように「処理単位」で一律に全体ロックを行うと、本来は衝突しない異なるデータに対する処理までもが待たされてしまい、著しいボトルネック（ロックコンテンション）が発生します。

おっしゃる通り、「データキー単位（キーX・キーY）でロックを取得する粒度の細かい制御（行ロック／行レベル排他制御）」へ変更することで、独立したデータに対する処理を完全に並列化できます。

具体的には、データベースが標準で持つ「行ロック（SELECT FOR UPDATE等）」**を活用するか、既存の**「ロックテーブルを拡張して行レベルで排他制御する」方法の2つのアプローチが考えられます。

---

### 排他制御のルール（マトリクス）

まず、各処理が必要とするキーと、同時に実行できる関係性を整理します。

* **処理A**：キー $(\text{X}, \text{Y})$ の両方を指定してロック
* **処理B**：キー $\text{Y}$ を指定してロック
* **処理C**：キー $\text{Y}$ を指定してロック

この条件において、各処理同士が衝突（処理待ち）するかどうかは以下の通りです。

| 処理 | 処理A（Key X, Y） | 処理B（Key Y） | 処理C（Key Y） |
| --- | --- | --- | --- |
| **処理A（Key X, Y）** | **同じ(X, Y)なら待つ**<br>

<br>(異なるX, Yなら並列可能) | **同じYなら待つ**<br>

<br>(異なるYなら並列可能) | **同じYなら待つ**<br>

<br>(異なるYなら並列可能) |
| **処理B（Key Y）** | **同じYなら待つ** | **同じYなら待つ** | **同じYなら待つ** |
| **処理C（Key Y）** | **同じYなら待つ** | **同じYなら待つ** | **同じYなら待つ** |

---

### 実装案1：DBの「行ロック（SELECT FOR UPDATE）」を利用する方法（推奨）

もしキーY（およびキーX）に対応するテーブルがDB上に存在するなら、既存のロックテーブルを使わず、**処理の対象となる実データレコードに対して行ロックを取得する**のが最もシンプルかつ高性能です。

#### 1. キーYを管理する親テーブル（例: `table_y`）を利用

処理A・B・C共通で排他の軸となるのは**キーY**です。そのため、キーYの行に対して `SELECT ... FOR UPDATE` を発行します。

* **処理Aの実装イメージ:**
```sql
BEGIN TRANSACTION;
-- キーYの行をロック（処理B・Cおよび別トランザクションの処理Aとの排他）
SELECT * FROM table_y WHERE key_y = 'Y_001' FOR UPDATE;

-- 必要に応じてキーXの行もロック
SELECT * FROM table_x WHERE key_x = 'X_001' FOR UPDATE;

-- 業務処理実行
...
COMMIT;

```


* **処理B・処理Cの実装イメージ:**
```sql
BEGIN TRANSACTION;
-- キーYの行をロック（処理Aおよび別トランザクションの処理B/Cとの排他）
SELECT * FROM table_y WHERE key_y = 'Y_001' FOR UPDATE;

-- 業務処理実行
...
COMMIT;

```

### 実装案2：ロックテーブルを「キー単位」に拡張する方法

実データテーブルを行ロックできない理由がある場合は、既存のロックテーブルの構造を「処理名単位」から「キー単位」に変更します。

#### 1. ロックテーブルの定義変更

ロックテーブル（例: `app_resource_locks`）にキー情報を保持できるようにします。

* **テーブル構造案:**
* `resource_type` (ロックの種類: `'KEY_X'` または `'KEY_Y'`)
* `resource_id` (キーの値: 例 `'X_001'` や `'Y_001'`)



#### 2. 各処理でのロック取得手順

* **処理Aの手順:**
1. ロックテーブルに対して、`resource_type = 'KEY_Y'`, `resource_id = キーYの値` の行を `SELECT FOR UPDATE`（なければINSERTしてからFOR UPDATE）。
2. ロックテーブルに対して、`resource_type = 'KEY_X'`, `resource_id = キーXの値` の行を `SELECT FOR UPDATE`。
3. 主処理を実行後、`COMMIT`（自動的にロック解除）。


* **処理B・処理Cの手順:**
1. ロックテーブルに対して、`resource_type = 'KEY_Y'`, `resource_id = キーYの値` の行を `SELECT FOR UPDATE`。
2. 主処理を実行後、`COMMIT`。

### 導入時の重要注意点：デッドロックの防止

キーを複数ロックする**処理A**において、ロック取得の順番が不統一だと**デッドロック**が発生するリスクがあります。

> **デッドロックの発生例:**
> * 処理A-1が 「キーX」 をロックした後に 「キーY」 をロックしようとする
> * 処理A-2が 「キーY」 をロックした後に 「キーX」 をロックしようとする
> 
> 
> → お互いが相手のロック解除を永久に待つ状態になります。

#### 対策

システム全体で「ロックを取得する順番のルール」を厳格に統一してください。

* **ルール例:** 常に **「キーY → キーX」** の順番でロックを取得する。
（処理B・CはキーYのみをロックするため、この順番を統一しておけば処理Aとのデッドロックを防げます）


---  


PostgreSQLの機能を最大限に活用した具体的な実装方法を提案します。

PostgreSQLでは、アプリケーション独自の排他制御のために「アドバイザリーロック（Advisory Lock）」という非常に強力で軽量な機能が用意されています。これを使えば、ロック用のテーブルを自作・管理することなく、**64ビット整数（または2つの32ビット整数）のキー値に対してメモリ上で高速にロック制御**が行えます。

---

### アドバイザリーロックによる実装案（推奨）

PostgreSQLの `pg_advisory_xact_lock()` を使用します。この関数は**トランザクション終了時（COMMITまたはROLLBACK）に自動的にロックが解放される**ため、解放漏れのリスクがありません。

文字列のキー（`Key X`, `Key Y`）は、PostgreSQLの `hashtext()` 関数を使って32ビット整数にハッシュ化して渡します。

#### 1. キーの種別定義（衝突防止）

キーXとキーYの値がたまたま同じ文字列だった場合に誤ってロックがバッティングしないよう、キー種別ごとにID空間を分けます。

* **キーY用 Namespace:** `1`
* **キーX用 Namespace:** `2`

#### 2. 各処理のSQL実装

##### 処理A（Key Y → Key X の順でロック）

デッドロックを防止するため、**必ず「キーY」を先にロックしてから「キーX」をロック**します。

```sql
BEGIN;

-- 1. キーYのロック取得 (Namespace: 1)
SELECT pg_advisory_xact_lock(1, hashtext('Y_001'));

-- 2. キーXのロック取得 (Namespace: 2)
SELECT pg_advisory_xact_lock(2, hashtext('X_001'));

-- 3. 主処理（UPDATE/INSERT/DELETE等）を実行
UPDATE target_table SET ... WHERE key_y = 'Y_001' AND key_x = 'X_001';

COMMIT; -- コミット時に自動的に両方のロックが解放される

```

##### 処理B・処理C（Key Y のみロック）

処理Bと処理CはキーYの情報しか持たないため、キーYのロックのみを取得します。

```sql
BEGIN;

-- 1. キーYのロック取得 (Namespace: 1)
SELECT pg_advisory_xact_lock(1, hashtext('Y_001'));

-- 2. 主処理を実行
UPDATE target_table SET ... WHERE key_y = 'Y_001';

COMMIT; -- コミット時に自動的にロック解放

```

### テーブル行ロック（SELECT FOR UPDATE）による実装案

既存のマスターテーブル（例: `master_y`, `master_x`）が存在し、それらを直接行ロックしたい場合は以下のように記述します。

```sql
BEGIN;

-- 処理Aの場合：必ず Key Y -> Key X の順序を守る
SELECT 1 FROM master_y WHERE key_y = 'Y_001' FOR UPDATE;
SELECT 1 FROM master_x WHERE key_x = 'X_001' FOR UPDATE;

-- 業務処理実行
...

COMMIT;

```

### 実装・運用におけるポイント

1. **ロックの順番を厳格に統一する**
処理Aのように複数キーを取得する場合は、システム全体で「必ず Key Y をロックしてから Key X をロックする」というルールを統一してください。順番が逆になる処理が存在するとデッドロックが発生します。
2. **ロック待ちタイムアウトの設定**
万が一のデッドロックや長期滞留を防ぐため、セッション単位またはトランザクション単位でロック待ちの制限時間を設定することをお勧めします。
```sql
SET LOCAL lock_timeout = '5s'; -- 5秒以上ロックが取れなければエラーにする

```
